# requirements-upsert

## 功能

手动维护项目级功能需求、非功能需求、架构约束、数据治理需求、安全合规需求及其实现状态。

本技能用于在用户明确要求以下任务时执行：

- 更新需求。
- 维护需求。
- 新增、修改、废弃需求。
- 根据代码状态刷新需求实现状态。
- 根据当前代码总结项目级需求。
- 检查哪些需求已实现、部分实现、待验证或未实现。
- 把用户手动新增的需求写入项目需求台账。
- 根据 ADR、项目说明、设计说明、代码或报告补充需求说明与需求跟踪表。

本技能是手动触发技能，不自动运行，不参与普通编码任务。

## 适用范围

本技能适用于任何软件项目，不限定具体仓库、业务领域、技术栈或目录名称。

如果项目存在以下文件或目录，应优先使用它们定位证据：

- 项目文件索引或目录树。
- 项目说明。
- 需求台账。
- ADR。
- 设计文档。
- 源码目录。
- 测试目录。
- 报告目录。

如果项目没有这些文件，应读取最小必要目录结构，并在输出报告中说明缺失项。

## 默认目标文件

默认维护：

```text
ai_shared/memory/project/项目功能与非功能需求.md
```

如该文件不存在，应创建。

如用户指定其他需求文件，以用户指定为准。

## 核心原则

1. 使用中文输出。
2. 手动触发，不自动运行。
3. 先读取项目文件索引或目录树，再定位相关文件。
4. 不默认读取全仓库。
5. 不读取与需求判断无关的低价值文件。
6. 不把每个函数、类、方法抽象成需求。
7. 不把每个测试用例、DTO 字段、配置项、环境变量抽象成需求。
8. 需求粒度必须站在架构师视角，面向业务能力、平台能力、架构能力、数据治理、安全合规和非功能约束。
9. 当前仓库文件是实现状态的事实来源。
10. 用户手动新增的需求是最高优先级需求来源。
11. 项目说明、ADR、报告和代码只能用于补充、校验或更新需求状态，不应无来源扩展业务范围。
12. 需求说明与需求状态必须分离。
13. 实现状态只维护在“需求跟踪表”中，不写入需求详细说明。
14. 更新需求时，必须同时维护“需求说明”和“需求跟踪表”。
15. 反馈必须简洁，重点说明新增、修改、删除、状态变化和未确认项。

## 默认忽略范围

扫描和读取时默认忽略以下内容，除非用户明确要求或它们与需求状态直接相关：

```text
third_party/
vendor/
node_modules/
.venv/
venv/
env/
__pycache__/
.pytest_cache/
.mypy_cache/
.ruff_cache/
.git/
.github/
.idea/
.vscode/
dist/
build/
target/
out/
coverage/
htmlcov/
logs/
tmp/
temp/
.cache/
*.egg-info/
```

默认忽略以下低价值文件：

```text
.gitignore
.gitattributes
.editorconfig
.prettierignore
.dockerignore
LICENSE
LICENSE.txt
package-lock.json
poetry.lock
Pipfile.lock
yarn.lock

```

说明：

- lock 文件、`.gitignore`、第三方库和构建产物通常不作为需求状态判断依据。
- 如果任务涉及依赖治理、许可合规、CI/CD、部署镜像、构建产物或安全扫描，可以按需读取相关文件。
- 如果 `project_tree.md` 中列出了这些文件，只用于导航，不展开分析。

## 来源优先级

当来源冲突时，按以下顺序处理：

```text
用户本轮明确指令
  > 用户手动维护的需求条目
  > 已接受 ADR / 架构决策
  > 当前源码与测试
  > 项目说明 / 设计说明
  > 只读探查报告 / 历史总结
```

说明：

- 本技能不负责从外部正式需求文档中提取需求。
- 如果用户已经在对话中或需求台账中提供了需求摘要，可按用户提供内容更新。
- 如果项目说明、报告或历史总结与当前代码冲突，以当前代码和测试作为实现状态判断依据。
- 如果 ADR 与当前代码冲突，应标记为“实现偏离 ADR”，不要自行修改 ADR。

## 必读文件顺序

执行时按以下顺序读取。

### 1. 项目目录树或文件索引

优先查找并读取：

```text
ai_shared/memory/project/project_tree.md
project_tree.md
docs/project_tree.md
```

如不存在，读取根目录下可用的 README、目录结构或文件列表。

用途：

- 定位需求文件。
- 定位项目说明。
- 定位 ADR。
- 定位相关源码。
- 定位相关测试。
- 定位相关报告。

目录树只作为导航，不替代读取当前源码。

### 2. 当前需求文件

默认读取：

```text
ai_shared/memory/project/项目功能与非功能需求.md
```

如用户指定其他文件，以用户指定为准。

读取后先判断：

- 是否已有相同或相近需求。
- 是否需要更新需求说明。
- 是否需要补充验收要点。
- 是否需要更新需求跟踪表。
- 是否需要标记废弃。
- 是否需要新增需求。
- 需求说明与跟踪表是否一一对应。

优先更新已有需求，不要重复新增同义需求。

### 3. 项目说明 / 设计说明

按目录树定位相关说明文件，例如：

```text
ai_shared/memory/project/项目说明.md
README.md
docs/
design/
architecture/
```

用途：

- 补充项目定位。
- 补充业务范围。
- 补充长期约束。
- 辅助识别宏观需求。

项目说明不能替代当前代码判断实现状态。

### 4. ADR / 架构决策

按目录树定位 ADR，例如：

```text
ai_shared/adr/
docs/adr/
architecture/adr/
```

只读取与本次任务相关的 ADR。

用途：

- 校验架构边界。
- 校验技术路线。
- 校验 use case、port、adapter、schema、消息契约等长期决策。

### 5. 代码和测试

根据目录树定位与本次需求相关的代码和测试。

读取重点：

- use case / application service。
- port / interface。
- adapter / infrastructure。
- composition / DI / wiring。
- runtime / scheduler / worker。
- domain model / entity / DTO。
- persistence / schema / migration。
- message / cache / storage adapter。
- 单元测试、集成测试、性能测试、端到端测试。
- skipped / xfail / mock-only 测试。

### 6. 报告

按需读取项目内报告，例如：

```text
ai_shared/reports/
docs/reports/
```

报告只能作为辅助证据。

报告结论必须尽量用当前代码或测试复核。

## 需求文件结构

需求文件必须包含两部分：

```markdown
# 项目功能与非功能需求

## 一、需求说明

### FR-001 需求标题

- 类型：功能需求
- 来源：用户指令 / ADR / 当前源码 / 项目说明 / 报告
- 来源文件：`path/to/file`
- 优先级：高 / 中 / 低
- 需求描述：
  - ...
- 验收要点：
  - ...
- 备注：
  - ...

## 二、需求跟踪表

| 编号 | 标题 | 类型 | 优先级 | 实现状态 | 当前实现证据 | 差距与下一步 | 最近更新时间 |
|---|---|---|---|---|---|---|---|
| FR-001 | ... | 功能需求 | 高 | 部分实现 | ... | ... | YYYY-MM-DD |
```

要求：

1. “需求说明”只描述需求本身，不写实现状态。
2. “需求跟踪表”维护实现状态、证据、差距和下一步。
3. 每个需求编号必须同时出现在“需求说明”和“需求跟踪表”。
4. 新增需求时必须同时新增说明条目和跟踪表行。
5. 更新状态时通常只改跟踪表；如需求含义发生变化，才同步修改需求说明。
6. 废弃需求保留需求说明和跟踪表行，跟踪表状态标记为“废弃”。

## 需求编号规则

功能需求：

```text
FR-001
FR-002
FR-003
```

非功能需求：

```text
NFR-001
NFR-002
NFR-003
```

架构约束：

```text
AR-001
AR-002
AR-003
```

数据治理需求：

```text
DGR-001
DGR-002
DGR-003
```

安全合规需求：

```text
SCR-001
SCR-002
SCR-003
```

编号一旦创建，不应随意重排。

废弃需求保留编号。

## 状态枚举

需求状态只能出现在“需求跟踪表”中。

只能使用以下状态：

```text
未实现
部分实现
已实现
待验证
不适用
废弃
```

状态含义：

- 未实现：当前没有可运行代码或测试证据。
- 部分实现：已有局部代码、接口、适配器、测试或切片，但未形成完整能力。
- 已实现：已有完整代码路径和自动化测试，满足当前验收要点。
- 待验证：代码存在，但关键集成测试、真实运行、性能测试或环境验证尚未完成。
- 不适用：该需求经确认不属于当前项目范围或当前阶段不适用。
- 废弃：需求已被替代或明确取消。

## 需求粒度规则

### 应写入的需求粒度

可以写入需求台账的内容包括：

1. 业务能力
   - 关键业务对象的生命周期管理。
   - 核心业务流程闭环。
   - 对外服务能力。
   - 业务规则、业务协同和业务集成能力。

2. 平台能力
   - 数据接入。
   - 数据处理。
   - 状态缓存。
   - 消息发布。
   - 存储管理。
   - 文件管理。
   - 任务调度。
   - 规则引擎。
   - 多协议接入。
   - 模拟器、本地开发与测试支撑。

3. 架构能力
   - 分层架构。
   - clean architecture / hexagonal architecture。
   - port-adapter。
   - 插件化。
   - 多后端可替换。
   - 模块边界。
   - use case / domain / infrastructure 职责边界。
   - 生产路径与测试工具路径边界。

4. 数据治理能力
   - 主数据。
   - 元数据。
   - 标签体系。
   - 数据质量。
   - 时间对齐。
   - schema 治理。
   - 版本管理。
   - 数据血缘。
   - 审计追踪。

5. 非功能需求
   - 性能。
   - 容量。
   - 延迟。
   - 可用性。
   - 可恢复性。
   - 可扩展性。
   - 可维护性。
   - 可观测性。
   - 可测试性。
   - 安全性。
   - 合规性。
   - 可替换性。
   - 部署适应性。

### 不应写入的需求粒度

禁止把以下内容单独抽象为需求：

1. 单个函数的功能。
2. 单个类的内部职责。
3. 单个方法的行为。
4. 单个 DTO 字段。
5. 单个配置项。
6. 单个环境变量。
7. 单个测试用例。
8. 临时 bug 修复。
9. 一次性脚本。
10. 普通重命名。
11. 普通代码风格调整。
12. 与架构能力无关的局部实现细节。
13. 某个内部 helper 的存在。
14. 某个异常类的存在。
15. 某个日志字段的存在。
16. 第三方库内部能力。
17. `.gitignore`、lock 文件、IDE 配置或构建缓存中的条目。

这些内容可以作为“当前实现证据”或“验收证据”，但不应成为独立需求条目。

## 从代码状态更新实现状态

判断实现状态时，应重点看：

- 是否存在用例层入口。
- 是否存在清晰端口或接口。
- 是否存在基础设施适配器。
- 是否存在依赖注入或组合根装配。
- 是否存在运行时调度或触发机制。
- 是否存在真实生产路径。
- 是否存在 mock-only、fake-only、simulator-only 情况。
- 是否存在自动化测试。
- 是否存在集成测试、性能测试或端到端测试。
- 是否存在 skipped / xfail 测试。
- 是否有配置示例和部署路径。
- 是否有错误处理、恢复机制和观测能力。

判断时必须区分：

```text
工具能力 ≠ 生产能力
接口存在 ≠ 能力实现
代码存在 ≠ 已装配
单元测试通过 ≠ 集成验证完成
mock 可用 ≠ 真实能力可用
simulator 可用 ≠ production client 可用
runner 存在 ≠ 业务链路已接入
配置项存在 ≠ 功能可用
报告说已完成 ≠ 当前代码已验证
```

## 更新流程

### 1. 定位文件

读取项目目录树或文件索引，找到本次任务相关文件。

不得跳过目录树直接凭记忆定位文件。

### 2. 读取需求文件

读取当前需求说明与需求跟踪表。

检查一致性：

- 需求说明中有、跟踪表中没有：补跟踪表行。
- 跟踪表中有、需求说明中没有：补需求说明或标记废弃。
- 编号重复：合并同义项，保留较早编号。
- 状态写在需求说明中：迁移到跟踪表。
- 跟踪表状态不在枚举中：修正为合法状态。

### 3. 分析用户本轮指令

判断用户是要求：

- 新增需求。
- 删除/废弃需求。
- 修改需求说明。
- 更新实现状态。
- 根据代码刷新状态。
- 根据 ADR 修正架构约束。
- 根据报告补充证据。
- 检查需求台账一致性。

### 4. 读取证据文件

只读取与本次任务相关的源码、测试、ADR、项目说明或报告。

不要全仓库扫描。

### 5. 更新需求说明

仅在以下场景修改需求说明：

- 用户新增需求。
- 用户明确修改需求含义。
- 现有需求说明过细，需要合并为架构师粒度。
- 现有需求说明过粗，需要拆分为少量宏观能力。
- 需求说明与已接受 ADR 或用户指令冲突。
- 跟踪表存在编号但说明缺失。

需求说明不写实现状态。

### 6. 更新需求跟踪表

在以下场景更新跟踪表：

- 实现状态变化。
- 当前实现证据变化。
- 差距与下一步变化。
- 优先级变化。
- 需求废弃或不适用。
- 最近更新时间变化。

跟踪表必须包含所有需求编号。

### 7. 处理冲突

如果发现冲突：

- 用户本轮指令与旧需求冲突：以用户本轮指令为准。
- ADR 与需求说明冲突：提示需要确认；已接受 ADR 不应被需求文件暗中覆盖。
- 当前代码与需求跟踪表冲突：更新跟踪表状态，并写明证据。
- 报告与当前代码冲突：以当前代码为准。
- 项目说明与需求文件冲突：不自动修改项目说明，报告中提示。

## 输出报告格式

完成后必须输出简短报告，并附“需求跟踪表变更摘要”。

格式：

```text
修改文件：
- ...

新增需求：
- FR-xxx 标题
- NFR-xxx 标题

更新需求说明：
- FR-xxx：说明调整点
- AR-xxx：说明调整点

更新跟踪表：
- FR-xxx：旧状态 -> 新状态，原因
- NFR-xxx：证据/差距更新
- AR-xxx：新增证据

废弃 / 不适用：
- FR-xxx：原因

仍需确认：
- ...

未读取 / 未验证：
- ...

需求跟踪表变更摘要：
| 编号 | 标题 | 变更类型 | 状态变化 | 证据/说明 |
|---|---|---|---|---|
| FR-xxx | ... | 新增/修改/状态更新/废弃 | 未实现 -> 部分实现 | ... |
```

要求：

- 报告不要冗长。
- 不要粘贴完整需求文件。
- 必须包含“需求跟踪表变更摘要”。
- 如果没有任何需求变化，也要说明“无需求变更”，并列出已验证依据。

## ADR 关系

需求台账不替代 ADR。

需求台账记录：

```text
要什么
做到什么状态
还差什么
```

ADR 记录：

```text
为什么这样设计
采用什么架构决策
拒绝了哪些方案
长期边界是什么
```

当需求更新产生长期架构决策时，应提示使用 ADR 技能，例如：

- 模块边界变化。
- use case / port / adapter 职责变化。
- 数据契约变化。
- 消息契约变化。
- schema 原则变化。
- 默认技术选型变化。
- 生产路径与工具路径边界变化。
- 安全控制策略变化。

## 禁止事项

1. 禁止把所有函数都抽象成需求。
2. 禁止把所有类都抽象成需求。
3. 禁止把临时任务日志写入需求台账。
4. 禁止未读目录树或文件索引就判断文件位置。
5. 禁止未读代码就判断实现状态。
6. 禁止把工具能力直接标记为生产能力。
7. 禁止把 skipped 测试当作已验证。
8. 禁止把 mock、fake、simulator 结果当作生产验收。
9. 禁止随意重排已有需求编号。
10. 禁止无来源新增业务范围。
11. 禁止把需求台账写成设计方案、日报或任务日志。
12. 禁止把实现状态写入需求详细说明。
13. 禁止只更新需求说明而不更新需求跟踪表。
14. 禁止只更新需求跟踪表而导致需求说明缺失。
15. 禁止读取第三方库、构建产物、缓存目录后把其中内容抽象为项目需求。
16. 禁止根据 `.gitignore`、IDE 配置、lock 文件推导业务需求。
