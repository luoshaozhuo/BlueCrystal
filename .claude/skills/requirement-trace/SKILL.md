# Skill: 需求跟踪表更新

## 目的

用尽量小的代价维护项目说明、需求文件和需求跟踪表。  
重点是：读取最少必要文件，准确判断需求状态，更新跟踪表，并输出简短报告。

---

## 使用场景

当用户要求：

- 更新需求状态
- 检查需求是否实现
- 维护功能/非功能需求文档
- 更新项目说明
- 更新需求跟踪表
- 根据代码核实需求完成情况
- 一次核验多个需求文件
- 生成多轮需求差距闭环计划

使用本 Skill。

---

## 工作边界

### 项目说明

项目说明只写稳定信息：

- 项目定位
- 业务范围
- 总体架构
- 长期边界
- 工程原则
- 安全与数据治理原则

不要在项目说明里写：

- 当前实现状态
- 测试结果
- 需求跟踪表
- 临时任务进度
- 某轮开发结果

### 需求文件

需求文件负责：

- 功能需求
- 非功能需求
- 架构约束
- 安全合规需求
- 测试验收需求
- 需求跟踪表

需求正文只写“系统应当具备什么能力”。  
实现状态只写在跟踪表里。

### 模块间边界

跨模块核验时必须区分：

- `source_lab` 是工具层 / simulator / probe / profile / capacity。
- `ingest` 是生产编排层 / use case / port / adapter / composition。
- 不得把 `source_lab` simulator closure 当作 ingest production ready。
- production ready、simulator closure、CI verified、framework closure 必须分别记录。

---

## 最小读取策略

不要全仓库无差别阅读。按任务范围读取。

### 必读

1. 项目说明文件
2. 需求 README 或需求索引
3. 目标需求文件
4. 项目目录树或 `tree` / `find` 结果
5. 相关 ADR / 报告索引

### 按需读取

根据需求编号和模块名称，只读取相关源码和测试。

例如：

```text
需求是 cache -> message：
读取 use case、port、adapter、composition、message publisher、相关测试。

需求是协议能力：
读取 protocol client、adapter、simulator、probe/profile/capacity 测试。

需求是安全/日志/审计：
读取 crosscutting、安全配置、审计、日志、指标相关代码和测试。
```

如果证据不足，停止扩大扫描，先把状态写为“待验证”或“部分实现”，并在报告中说明缺失证据。

### 多需求文件

一次核验多个需求文件时：

1. 先列出每个文件的需求编号。
2. 分模块读取证据，不混用证据。
3. 每个需求文件原地更新自己的需求跟踪表。
4. 报告中按文件汇总上调、下调、保持、暂不支持和证据不足。

## 状态枚举

跟踪表中的实现状态只使用：

```text
未实现
部分实现
代码完成待验证
测试通过
运行闭环通过
暂不支持
已废弃
```

## 验证等级

```text
L0：代码存在
L1：单元测试通过
L2：集成测试通过
L3：E2E / simulator / 外部依赖验证通过
L4：profile / capacity / 性能专项通过
L5：运行闭环通过
```

---

## 状态判定规则

### 未实现

满足任一条件：

- 找不到相关生产代码
- 只有空目录、占位文件、TODO、pass
- 只有文档，没有实现
- 只有 mock 测试

### 部分实现

满足任一条件：

- 有部分代码，但调用链不完整
- 有接口，无实现
- 有 adapter，无 backend
- 有 use case，无 composition 接入
- 有测试，但只覆盖局部或 happy path

### 代码完成待验证

满足全部条件：

- 生产代码路径基本完整
- 能被 composition / factory / route 装配
- 主路径无明显 TODO / pass / NotImplementedError
- 缺少足够测试或运行证据

### 测试通过

满足全部条件：

- 生产代码存在
- 单元或集成测试通过
- 测试覆盖主要成功路径和至少部分失败路径
- 不是纯 mock 测试

### 运行闭环通过

满足全部条件：

- 生产代码路径完整
- 有真实或可控外部依赖验证，例如 simulator、test container、真实服务
- 覆盖完整业务链路
- failed = 0
- skipped 不作为完成证据

CI pending、权限不足、load gate 未执行时，不得写“运行闭环通过”。

### 暂不支持

满足全部条件：

- 能力属于长期边界
- 当前阶段明确不支持
- 代码返回 NOT_IMPLEMENTED 或等价状态
- 测试证明不会假成功或崩溃

### 已废弃

满足全部条件：

- 有 ADR、报告或迁移说明
- 有替代实现或替代需求
- 旧路径不再被生产代码引用

## 检查深度

每条需求至少检查：

1. 入口：route / CLI / composition / factory / scheduler
2. 业务逻辑：use case / service / role
3. 边界：port / interface
4. 实现：adapter / backend
5. 外部依赖：cache / MQ / DB / protocol / file / API
6. 测试：unit / integration / E2E / profile / capacity
7. 异常：timeout / failure / unsupported / retry / cleanup

不要求无限深挖。  
如果 15 分钟内无法确认，应记录“证据不足”，不要扩大成全仓扫描。

---

## 不得作为完成证据

以下内容不能单独证明完成：

- 文件存在
- 类名存在
- 函数存在
- README 声称支持
- mock 测试通过
- skipped 测试
- TCP connect 成功
- fake OK
- 内部字典读写
- 未接入 composition 的代码
- 测试工具能力

特殊边界：

- GOOSE/SV 需要 root 或 CAP_NET_RAW 与可用 L2 interface；无权限时只能写 framework closure + CI pending。
- IEC101 / Modbus RTU gateway mode 不能等同真实串口硬件验收。
- load gate 未执行必须写“测试未执行”和原因。
- source_lab 能力不能作为 ingest 生产能力证据。

## 跟踪表字段

每个需求文件使用统一字段：

```text
| 编号 | 上承需求 | 标题 | 类型 | 优先级 | 责任模块 | 验证等级 | 实现状态 | 实现证据 | 验收测试 | 差距 | 下一步 | 更新时间 |
```

证据要短，但必须可定位。

示例：

```text
实现证据：
src/app/usecases/publish.py; src/app/adapters/kafka.py; tests/integration/test_publish.py

验收测试：
pytest tests/integration/test_publish.py -q -> passed
```

未执行测试时写：

```text
测试未执行
```

不要写“应可通过”。

证据要求：

- 实现证据必须短路径定位到源码、测试、ADR 或报告。
- 验收测试必须写实际命令和结果。
- 未执行测试必须写“测试未执行：原因；建议命令：...”。
- skipped 只能作为条件说明，不能作为 passed。

---

## 更新规则

### 只在必要时改需求正文

可以改正文的情况：

- 新增需求
- 删除已废弃需求
- 修改验收标准
- 调整模块承接关系
- 修正明显重复或错误

### 状态变化只改跟踪表

实现状态变化只更新：

- 验证等级
- 实现状态
- 实现证据
- 验收测试
- 差距
- 下一步
- 更新时间

更新时记录前后状态判断：

- 上调：证据等级或实现状态提高。
- 下调：发现证据不足、skip、mock、边界混淆或未接入。
- 保持：证据无变化。
- 暂不支持：长期边界明确且有 NOT_IMPLEMENTED 或等价测试。

---

## 测试策略

优先运行最小相关测试，不默认全量测试。

```text
1. 先运行目标需求相关测试。
2. 如果修改公共能力，再运行相关模块测试。
3. 只有用户要求或改动范围很大时才跑全量测试。
```

不得在未执行测试时写“测试通过”。

## 三轮闭环

如果用户要求多轮完成：

```text
第1轮：核验 + 跟踪表更新 + 差距清单
第2轮：补高优先级差距 + 更新跟踪表
第3轮：最终验证 + final trace closure
```

差距任务按风险排序，优先：

1. 架构边界破坏。
2. 主业务链路缺口。
3. 写入/控制安全与审计缺口。
4. 多协议 adapter 缺口。
5. 故障恢复 / reconnect baseline 缺口。
6. observability / metrics / audit 缺口。
7. 安全分区文档缺口。

---

## 报告要求

每次执行后新增一个简短报告：

```text
reports/requirements_trace_update_<date>_<scope>.md
```

如果项目已有报告目录，使用项目目录。

报告只写：

```text
1. 本次范围
2. 读取文件
3. 更新文件
4. 执行测试
5. 状态上调
6. 状态下调
7. 保持
8. 暂不支持
9. 证据不足
10. 运行归档 / CI 验证状态
11. 必须在后续轮次补齐的差距
12. 下一步
```

报告要短，不要复述所有需求全文。

---

## 禁止事项

- 不要为了状态好看降低验收标准
- 不要把 skipped 当 passed
- 不要把 mock 测试当运行闭环
- 不要把目录存在当模块完成
- 不要把测试工具能力当生产能力
- 不要把需求正文改成实现说明
- 不要在项目说明中写实现状态
- 不要删除未实现需求来掩盖差距
- 不要全仓无差别扫描
- 不要输出超长报告

---

## 推荐流程

```text
1. 识别本次 scope。
2. 读取项目说明、需求索引、目标需求文件。
3. 读取目录树或快速扫描相关目录。
4. 按需求编号建立检查清单。
5. 对每条需求追踪最小调用链。
6. 查找相关测试。
7. 运行最小必要测试。
8. 更新跟踪表。
9. 必要时回填项目级聚合状态。
10. 输出简短报告。
```
