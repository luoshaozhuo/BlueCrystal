# 测试规则

## 1. 规则定位

本规则定义测试分类、测试结果、回归测试和测试索引维护方式。测试分类按软件生命周期阶段组织；具体命令由仓库工具链、`validation-routing.md` 和测试索引共同决定。

## 2. 软件生命周期测试阶段

测试应归入以下阶段之一。阶段用于说明测试目的和执行时机，不强制等同于物理目录结构。

| 编号 | 阶段 | 目标 | 常见对象 |
|---|---|---|---|---|
| P1 | 开发期验证 | 验证本地逻辑、接口约束、边界条件和错误路径 | 单元测试、契约测试、解析/转换测试、fake/mock/stub 语义测试 |
| P2 | 构建期验证 | 验证代码、脚本、配置和包结构可构建、可导入、可静态检查 | 编译、lint、type-check、import boundary、脚本语法检查 |
| P3 | 模块集成期验证 | 验证单一模块内部组件协作 | use case + adapter、repository、scheduler、临时文件/SQLite/local server |
| P4 | 跨模块联调期验证 | 验证多个模块之间的数据流和调用链路 | API 到 use case、消息管道、存储链路、simulator-backed 链路 |
| P5 | 准生产依赖验证期 | 验证真实或等价外部依赖下的行为 | 数据库、消息队列、缓存、对象存储、时序库、外部服务 |
| P6 | 部署前验收期 | 验证部署配置、运行入口、预检脚本和最小 smoke | Docker/Compose、entrypoint、health/ready、migration、rollback/switchover |
| P7 | 发布后运维验证期 | 沉淀运行问题、故障恢复、容量、性能和可观测性验证 | 运行问题复现、故障注入、长稳、性能基线、告警和审计检查 |

发布回归不是独立生命周期阶段，而是从上述阶段中选择测试形成回归套件。

## 3. 测试结果

测试执行结果只允许：

| 结果 | 含义 |
|---|---|
| PASS | 已执行且通过 |
| FAIL | 已执行且失败 |
| NOT_RUN | 未执行，必须说明原因 |

`NOT_RUN` 不是通过结果，不得计入通过数量。常用原因码：

| 原因 | 说明 |
|---|---|
| OUT_OF_SCOPE | 不属于本次验证范围 |
| MISSING_ENVIRONMENT | 缺少运行环境、服务、硬件或配置 |
| MISSING_DEPENDENCY | 缺少库、二进制、工具或镜像 |
| MANUAL_REQUIRED | 需要人工步骤或受控现场条件 |
| TOO_EXPENSIVE_FOR_THIS_RUN | 本次执行成本过高，例如长稳、压测、大规模数据 |
| USER_NOT_REQUESTED | 用户或任务未要求执行 |

测试框架产生的 skip/xfail 必须在报告中转写为 PASS、FAIL 或 NOT_RUN；其中未实际执行的 skip 应转写为 NOT_RUN 并说明原因。

## 4. 测试索引

仓库应维护唯一测试索引，默认位置为：

```text
ai_shared/memory/test_index.md
```

测试索引用于记录测试资产和回归套件，不替代测试文件、CI 配置或报告。建议包含：

```text
1. 生命周期阶段定义；
2. 测试资产索引；
3. 回归测试索引；
4. 回归套件组合；
5. 工具/实验测试与生产测试的边界；
6. 维护规则。
```

回归测试统一登记在测试索引中，不为不同回归来源单独创建索引文件。

## 5. 回归测试

回归测试按来源分类，但统一维护在测试索引中：

| 来源 | 说明 |
|---|---|
| defect-regression | 缺陷修复后新增或固化的回归测试 |
| operation-regression | 运行、部署、运维或故障恢复中发现问题后的回归测试 |
| compatibility-regression | API、schema、配置、消息格式、协议兼容性回归 |
| chain-regression | 跨模块链路、主流程或关键业务流回归 |
| release-regression | 发布前组合回归套件 |

回归测试状态建议使用：

```text
ACTIVE      当前有效，相关变更或发布前应执行；
RETIRED     已退役，必须记录原因；
SUPERSEDED  已被更完整测试替代，必须记录替代项。
```

## 6. 测试目录边界

目录命名可以按仓库习惯保留，例如 `unit/`、`integration/`、`e2e/`、`performance/`。生命周期阶段应通过测试索引、marker、文件头或测试说明表达。

生产代码测试、工具测试、实验测试应边界清楚：

1. 生产路径测试验证可交付行为和跨模块契约。
2. 工具/实验模块测试只证明工具/实验模块自身行为。
3. 工具测试通过不得自动等同于生产链路通过。
4. 生产测试不得依赖未声明的工具运行时或测试专用路径。
5. 如果工具测试可复用为生产边界测试，应在测试索引中明确其边界和不能证明的能力。

## 7. Marker 规则

marker 用于执行选择，不是测试分类的唯一来源。仓库可按需要定义 marker，但应遵守：

1. marker 含义必须在测试索引或测试说明中可追溯。
2. 外部依赖、慢速、长稳、性能、人工条件相关 marker 必须说明执行条件。
3. fake/mock/stub/simulator 测试不得用 marker 伪装成真实外部依赖验证。
4. 历史 marker 可以保留，但应在测试索引中说明当前语义和迁移方向。

## 8. 代码变更后的测试同步

发生以下变化时，必须同步评估和更新测试、fixture、fake/mock/stub、测试索引及必要文档：

1. 行为变化；
2. public interface、port、Protocol、ABC、API、CLI 变化；
3. schema、配置、环境变量、迁移、消息格式、协议帧变化；
4. adapter、repository、gateway、driver 的外部依赖语义变化；
5. 权限、审计、幂等、重试、超时、事务、lease/fencing、回滚等运行时语义变化。

测试失败时不得默认回滚生产代码以迎合旧测试。应先判断：

```text
1. 生产代码缺陷；
2. 测试断言过期；
3. 需求或契约已变化，测试需要更新；
4. 环境或依赖缺失；
5. 既有失败。
```

## 9. 禁止事项

1. 不把“能运行不报错”当作有效测试。
2. 不降低断言、删除失败测试、扩大 skip 或吞异常制造通过。
3. 不把未执行、mock、fake、stub、health check、脚本存在、单文件通过写成真实闭环。
4. 不只跑局部测试却声称全量通过。
5. 不新增无条件 skip 掩盖缺陷。
6. 不把测试工具能力写成生产能力。
