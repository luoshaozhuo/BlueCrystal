# 文档、目录树与规则维护

## 1. 基本原则

1. 长期文档只记录稳定事实、规则、决策和背景。
2. 只有用户明确要求归档时，任务过程和验证结果才进入报告；不写入长期规则、需求文档或目录树。
3. 不把未验证项写成通过。
4. 不重复维护两套规则。
5. 规则文档保持单一来源和通用表达；语言差异作为通用规则下的分节处理。
6. 文档、需求和报告不得把 mock、fake、stub、health check、脚本存在、局部通过或未执行项写成真实闭环。

## 2. 目录树

1. 项目目录树应保持文件级条目。
2. 目录树为手动维护项；只有用户明确要求时，才由当前主会话执行 `project-tree-update` 或 `project-tree-reset`，不对普通文件变化做自动检查。
3. 每个 item 职责说明应简短。
4. 不得只写到目录层级。
5. 目录树只用于导航，不能替代读取真实源码、测试、配置和 schema。

## 3. 需求与状态跟踪

1. 只有用户明确要求更新需求或任务状态时，才按项目规则更新跟踪表或等价索引。
2. 不得把 skipped、mock、fake、health check、TCP connect、脚本存在、局部通过或 NOT_RUN 写成真实通过。
3. 发现状态高估时，必须降级或改为明确的未验证说明。
4. 状态必须和实际验证类型一致。

## 4. 报告归档

1. 报告归档仅由用户明确要求，不因编码、测试或验证阶段自动触发，也不维护第二套报告流程。
2. 报告必须遵守 `reporting.md` 的语言、位置、命名、格式和结果规则。
