# Whale 项目说明

## 1. 文件定位

本文件保存 Whale 项目的稳定背景、建设目标、业务范围、长期边界和工程原则。

本文件不承担详细需求管理职责，不维护实现状态，不维护需求跟踪表。Whale 的项目级和模块级功能/非功能需求以 `ai_shared/requirements/` 目录下的正式需求文件为准。

当本文件与正式需求文件冲突时，以正式需求文件为准。当前源码、测试、报告和 ADR 仅用于判断实现状态，不用于反向削弱正式需求边界。

## 2. 项目定位

Whale 面向并网风光储电厂多源数据接入、汇聚、处理、治理、存储与服务，目标是形成统一、可扩展、可替换、可长期运行的数据基础平台。

平台不是单一采集子系统，也不是单一存储系统，而是覆盖多源数据接入、消息管道、速度层、原始层、批处理层、标准层、数仓与服务层的一体化数据基础设施。

## 3. 业务范围

平台覆盖生产运行现场设备数据、第三方系统数据、离线数据、仿真模型及仿真结果数据。

主要接入对象包括：

- 风电机组运行状态、功率、电压电流、偏航、变桨、振动、温度、故障状态、控制状态等数据。
- 储能 PCS、BMS、电池簇、电池舱、温控、消防及辅助系统数据。
- 测风塔及环境感知设备数据。
- POC 测点及并网点功率、电压、电流、频率、功率因数、电能质量等数据。
- 激光雷达多高度层、多距离门、风速、风向、湍流、切变等数据。
- 第三方系统数据，包括结构化数据、时序数据、事件数据、统计数据和半结构化数据。
- 仿真模型、模型版本、输入参数、工况配置、仿真结果文件及结果数据集。
- 经安全论证允许接入的其他生产辅助系统数据。

## 4. 总体数据架构

Whale 采用 Kappa 与 Lambda 混合的数据处理架构。

实时链路：

```text
source
-> ingest
-> message pipeline
-> speed layer
-> raw storage
-> serving cache / business cache
```

批处理链路：

```text
raw storage
-> batch layer
-> processing
-> standard layer
-> aggregation / warehouse / mart / service
```

其中：

- ingest 负责生产 source 接入、状态缓存、消息发布和控制写入边界。
- message pipeline 负责异步解耦、消息留存、消息回放和消费组管理。
- speed layer 负责消费实时消息、写入原始层、更新业务侧缓存。
- storage 负责 raw、standard、warehouse/mart、serving cache 等存储层次。
- batch layer 负责定期从 raw storage 读取数据并触发批处理。
- processing 负责清洗、标准化、时间对齐、质量处理和回灌。
- aggregation 负责实时聚合、周期聚合和业务主题聚合。

## 5. 长期能力边界

平台应形成以下长期能力：

- 多源异构数据统一接入。
- 多协议设备数据采集、订阅、报告、解析与必要控制写入。
- 高频时序数据持续接入、缓存、处理、存储和查询。
- 消息管道解耦、速度层实时处理、批处理层周期处理。
- raw、standard、warehouse/mart、serving cache 等数据层次。
- 结构化、半结构化、文件类、模型类数据统一纳管。
- 场站、设备、测点、事件、告警、模型对象、文件对象、结果对象的统一建模。
- 标签体系、主数据体系、元数据体系和信息模型管理。
- 数据标准化、数据质量管理、时间质量管理、时间基准对齐。
- 补采回灌、版本兼容、审计追踪。
- 对内支撑采集、治理、分析、监测、建模等模块。
- 对外提供规范化、可管控、可配置、可演进的数据服务接口。
- 缓存、消息、数据库、接口、对象存储等关键组件可配置替换。

## 6. 性能、容量与时效目标

平台应支持一个或多个电场范围内数百台风机及储能、测风塔、POC、激光雷达等配套设备接入。

典型高频场景目标为：单台设备约 10Hz、约 600 字段规模的数据持续接入，并支持吞吐、缓存、处理、存储与查询能力随场站规模横向扩展。

平台应支持突发流量、短时堆积、链路波动、集中补采、第三方批量同步和仿真数据批量入库等场景下的缓冲、削峰、分批处理、断点续传和失败重试。

实时监视类数据应满足秒级可见和近实时服务要求；第三方系统同步和仿真数据纳管按业务周期或任务触发处理。

## 7. 安全合规与业务边界

平台必须服从电力监控系统安全防护、网络安全、数据安全、等级保护、关键信息基础设施保护以及现场安全分区分域要求。

平台应坚持安全边界先行，明确生产控制大区、管理信息区及边界区域的功能部署、数据范围、通信方向、边界访问控制、协议收敛、最小开放面和最小权限。

平台原则上不承担以下职责：

- 不承担现场一次设备或二次系统的保护与控制逻辑。
- 不替代 SCADA、保护、测控、PCS、BMS 等原系统的核心控制功能。
- 不作为未经安全论证的跨安全分区自由数据交换通道。
- 不在未满足安全边界、授权、审计和风险控制要求的前提下提供控制反向下发能力。

## 8. 工程方法

本项目采用低成本自动化驱动、项目记忆增强的演化型增量迭代开发方式。

- 目标稳定，路径演化。
- 先完成可运行切片，再通过测试、性能、异常场景暴露问题。
- 小步实现、小步验证、小步总结。
- 发现结构阻碍后按需重构。
- 能自动化的工作不依赖 agent 反复口头执行。
- 文档治理保持精简，不把任务日志写成长久规则。

## 9. 数据与配置治理原则

数据库 schema、字段名、表关系必须以当前 ORM、migration、schema 文件为准。配置项必须以当前配置模型、环境变量解析、示例配置和测试为准。

禁止凭记忆推断字段、创建无来源字段、用测试结构替代生产契约。
